편집기실험 결과기초 교재 ↗

이 예제는 실제 미리캔버스 내부 구현을 재현하지 않습니다. 먼저 결과를 예상하고 조작한 뒤, 오른쪽 상태와 요청을 근거로 설명해 보세요. 아래 정답은 실험 후 펼칩니다. 학습 이해도는 아직 측정하지 않았습니다.

1. 문서와 선택, 이력은 서로 다른 값

문서는 저장할 내용입니다. 선택은 지금 조작하는 요소의 ID이고, 이력은 문서의 이전·현재·다음 snapshot입니다. 서버 revision은 저장 순서이므로 undo로 되돌리지 않습니다.

  1. 새 문서를 만들고 텍스트와 사각형을 추가하세요. 제목·텍스트는 입력 후 Tab 또는 다른 곳을 클릭하면 한 편집으로 확정됩니다.
  2. 사각형을 여러 번 움직인 뒤 undo를 한 번 누르면 어디로 갈지 먼저 예상하세요. 드래그 한 번과 방향키 한 번의 차이를 확인하세요.
  3. undo 후 새 텍스트를 추가하세요. redo가 남아 있을까요? 문서 JSON과 undo / redo 수를 비교하세요.
  4. 요소를 캔버스 밖으로 이동해 보세요. 좌표가 어떤 값에서 멈추는지 설명하세요.
관찰 해설

pointer move는 미리보기이고 pointer up에서 한 번만 history에 기록합니다. pointer cancel은 출발 snapshot을 복구합니다. 새 편집은 future를 비우며 최근 50개 과거 snapshot만 남습니다. 선택 자체는 undo 대상이 아닙니다. 방향키는 1px, Shift와 함께 누르면 10px입니다.

2. 화면의 최신 상태와 저장된 상태

저장 버튼은 그 순간의 snapshot과 마지막으로 확인한 revision을 보냅니다. 저장 중에 새 편집을 하면 이전 snapshot의 저장 성공이 새 편집까지 저장했다는 뜻은 아닙니다. 중복 저장과 문서 전환은 응답까지 잠깁니다.

  1. 저장하고 주소의 #문서ID를 포함한 URL을 두 번째 탭에 여세요.
  2. A 탭에서 제목을 바꾸고 저장하세요. B 탭에서도 다른 제목으로 바꾼 후 저장하기 전에 결과를 예상하세요.
  3. B의 409와 로컬 제목, 서버 revision을 확인하세요. 서버 확인만으로 내 제목이 바뀌는지 관찰하세요.
  4. 필요하면 내 작업 JSON을 내려받고, 서버 내용으로 교체하세요. 자동 병합은 없습니다.
관찰 해설

비교와 쓰기를 한 lock 안에 두므로 같은 revision을 보내는 두 저장 중 하나만 성공합니다. atomic replace는 기존 JSON이 중간까지만 쓰이는 상황을 줄입니다. 이것은 DB transaction, 여러 서버의 lock, 정전 시 완전한 durability를 구현한 것이 아닙니다. 한 프로세스만 같은 data 디렉터리를 사용해야 합니다.

3. 실패를 두 종류로 나누어 보기

  1. 제목을 바꾸고 ‘기록 전 실패’를 선택해 저장하세요. 서버 파일과 로컬 내용 중 무엇이 바뀔지 예상하세요.
  2. 정상 저장으로 다시 시도하세요. 다음에는 ‘기록 후 응답 유실’을 선택하세요.
  3. 결과 불명에서 바로 재시도하면 어떻게 될까요? 먼저 서버 확인으로 제목과 revision을 비교하세요.
  4. 터미널에서 python3 experiments/run.py를 실행하세요. 원시 기록에서 보호군과 고장 낸 대조군을 비교하세요.
관찰 해설

503 주입은 파일 기록 전에 멈춥니다. 응답 유실은 기록 후 연결을 닫아 브라우저가 성공 여부를 모르게 합니다. 같은 expected_revision으로 재시도하면 이미 revision이 증가해서 409가 납니다. ‘오류를 받음’과 ‘기록되지 않음’은 동의어가 아닙니다. 대조군은 임시 디렉터리에서만 version 검사를 생략하고 B가 A의 제목을 덮는 lost update를 보입니다.

4. 라이브러리가 맡은 일, 직접 만든 일

React나 편집 엔진을 쓰면 렌더링·상태 연결·선택 도구 일부를 맡길 수 있지만, 충돌과 저장의 의미가 자동 해결되지는 않습니다. 여기서는 학습할 코드 경로를 짧게 하기 위해 직접 구현했습니다. 큰 문서의 history 메모리, 복잡한 텍스트 편집, 접근성·공동편집을 제품 수준으로 확장하려면 별도 판단이 필요합니다.

DB index 실험은 앱의 JSON 저장과 분리됩니다. 실제 DB 측정 여부는 결과 페이지의 기록을 확인하세요. MOCK 비동기 작업은 이번 앱에 넣지 않았습니다. 실제 RabbitMQ의 exchange·queue·ack·publisher confirm과 메모리 mock의 차이는 기초 교재에서 이어갑니다.
